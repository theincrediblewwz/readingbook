# 2026-10-30 多组件优化结果（交付前初稿）

本批已有三处获得独立对照支持的实际产品改动：缩小对话草稿的观察范围、空历史提前返回、复用同次组合查询中的实体时间快照。它们减少重复工作，没有更换阅读引擎、添加依赖或改变原书、笔记、分析的存储格式。

**状态边界：三处改动已进入本地产品源码；完整产品回归、PDF 当前条件 FPS、GitHub 同步及安装替换由主执行者补充。本文不表示已经发布或本批全部完成。** 基线为 main `c5540152aa6a9e38625c28c444144c8bb2728b06` / 产品 0.23.15。诊断使用合成内容、隔离书库和工作区内产物，没有以模型响应时间冒充本地性能。

## 1. 对话输入：草稿只更新输入区

原 `BookChatContent` 同时观察 `QueryComposerDraft`、持有历史列表，并在回答卡片里准备 Markdown。即使模型文字未变，草稿发布也可能让历史所属 View 重新求值。

`Sources/ReadingBook/ChatSaveViews.swift` 现在由父层普通持有同一草稿对象，只有固定位置的 `BookChatComposer` 使用 `@ObservedObject`。父层仍拥有 FocusState、发送回调、历史、记忆、审阅和回答保存状态。发送时通过对象引用读取最新草稿，不提前捕获旧字符串；保存、原文身份和选区守护保持原逻辑。这不是增加历史缓存，也没有放宽 Markdown 身份比较。

正式对照使用真实 SwiftUI 输入区和 Markdown/WebKit 历史：8 条消息，其中一条回答分别为 20 KiB 或 512 KiB。每进程按 20 ms 节奏提交 100 次草稿变更，固定 4 秒窗口采样自身 App 的 user+system CPU；不是在跑满 CPU 后按完成任务数重新挑窗口。

| 合成回答大小 | 固定窗口 CPU 配对节约 | 配对相对节约 | 历史 body / Markdown prepare 次数 |
| --- | --- | --- | --- |
| 20 KiB | 160.795 ms；三对均节约 | 22.0% | 每对少 100 次历史 body、212 次 prepare；候选均为 0 |
| 512 KiB | 1,369.680 ms；三对均节约 | 71.9% | 每对少 93–95 次历史 body、198–202 次 prepare；候选均为 0 |

这是本批最直接的原生交互收益：输入新问题时，减少重新处理未变化旧回答的工作。各进程都验证最终草稿字节、实际原生输入文字、完整 DOM、项目指纹、前台状态及零模型请求；非草稿的 Store 发布没有混入计时窗口。

代价也保留在结论里：20 KiB、512 KiB 的自身 App 端点 footprint 配对中位增加分别为 147,528 B（约 0.141 MiB）、983,136 B（约 0.938 MiB），均通过预定回退门槛。因此不能把本项称为内存下降。语义更新延迟的配对中位变化分别约 −0.040 ms、+0.123 ms，均通过 10 ms 绝对下限守护。

这里的延迟是“草稿模型变更到输入子 View 语义更新”，不是操作系统键盘事件、中文 IME 或首像素延迟。现有 driver 未保存第一次最终语义更新的全部原始 ticks，独立分析用最后输入/截止证明约束其上界，没有声称精确重算了第一次更新时间。自身 App 资源也不包括 WebContent、GPU 或整机内存。

## 2. 历史匹配：已知空结果就不再准备上下文

`Sources/ReadingCore/ReadingChatHistory.swift` 在按对话模式和讲解方式筛选历史后加入 `guard !matching.isEmpty else { return [] }`。没有符合记录时，原结果必然为空，不再建立当前上下文指纹、原文和文档索引；匹配非空时继续执行原本完整的身份、范围、版本和防剧透检查。

数据来自 1,484 个合成原文单元。每个新进程调用 8 次，首次单列，后 7 次中位数作为该进程的 warm 值；7 次不当作 7 个独立样本。

| 范围 / 历史条件 | warm wall 基线中位数 → 候选中位数 | warm wall 配对节约 | 判断 |
| --- | --- | --- | --- |
| 整书、没有历史 | 1.140 ms → 计时分辨率附近 | 1.140 ms；约 100% 的该局部成本 | 目标通过；warm CPU 差值出现分辨率内的 0，不称为零成本 |
| 整书、有历史但模式/风格均不匹配 | 1.124 ms → 0.015 ms | 1.110 ms；98.6% | 目标通过，CPU 配对节约约 1.111 ms |
| 整书、有兼容历史 | 28.366 ms → 28.182 ms | 0.183 ms | 回退守护通过；没有把这点波动作为优化目标 |
| 完整 `ReadingPreparedAnswer.freeze`，无历史 | 27.759 ms → 26.945 ms | 0.994 ms，配对相对节约约 3.5% | 整链小幅收益；远小于局部的接近 100% |
| 完整 `ReadingPreparedAnswer.freeze`，有兼容历史 | 55.876 ms → 55.852 ms | 实际配对中位增加 0.260 ms | 回退守护通过；两个显示中位数不能代替配对差值 |

页范围空历史也通过首次/warm 回退守护；完整 freeze 两个场景的首次调用同样通过。此处“完整”仅指本地 `freeze` 准备链，不包含网络、模型生成或最终 UI 展示，不能说整次 AI 提问快了 98.6%。

本项没有新增保留式缓存。lifetime peak RSS 辅助观测中，整书空历史、筛掉的历史、无历史完整 freeze 的配对中位分别少约 0.672、0.797、1.625 MiB；RSS 是进程峰值辅助指标，不是 physical footprint，也不是运行中 ReadingBook 的常驻内存承诺。

## 3. 组合组件：只复用同一次不可变输入的时间快照

`CompositionRuntime.project(prepared)` 原本已有 scope base、事件、关系及遍历缓存。缺口是同一实体的时间快照：时间行、地图、地点关联及多个 source 可能反复调用完整 `entitySnapshot`，重复建立来源、对象、事件和关系投影。

`Sources/ReadingCore/CompositionRuntime.swift` 仅扩展现有局部 `TemporalQueryCache`：键包含 `scope + entityID + 实际 point/window`，最多保留 200 项，生命周期是一次同步 `project()`。同一 scope 绑定 prepared 中唯一的不可变源书/范围/边界；没有跨请求、跨书或跨 await 复用。未命中仍调用原公开 API，保留全部来源验证；命中前及计算后检查取消。超过 200 项继续计算，不丢结果。时间行按 point 查询，窗口地图按实际 window 查询，避免把两者当成同一次操作。

基准为 1,000 人物、1 或 4 个 source，每 source 最多 80 行；压力场景改为 200 行。主指标覆盖实际 `prepare + project` 整链，包含准备成本。

| 场景 | 整链 wall 基线 → 候选中位数 | 整链配对 wall / CPU 节约 | 结果 |
| --- | --- | --- | --- |
| 单 source 纯列表 | 175.174 → 178.818 ms | **增加** 3.851 / 3.869 ms | 约 2.2% wall 回退，通过预定 5% 守护；无重复快照时不能称为收益 |
| 四 source 纯列表 | 231.722 → 176.682 ms | 53.108 / 53.032 ms；23.1% / 23.1% | 收益与回退门槛通过 |
| 单 source 地图 | 190.052 → 173.927 ms | 16.199 / 16.185 ms；8.5% / 8.5% | 有观察收益，但未达到本组预定 10% 收益门槛 |
| 四 source 地图 | 305.985 → 178.913 ms | 127.072 / 127.056 ms；41.6% / 41.6% | 收益与回退门槛通过 |
| 四 source 地图、200 行压力 | 541.529 → 208.277 ms | 331.136 / 330.887 ms | 压力回退守护通过；未事后提升为主收益目标 |

局部解释与整链分别看：四 source 纯列表的 `project` wall 中位数约 84.748 → 28.541 ms，四 source 地图约 158.452 → 29.354 ms；各自配对节约约 56.207、129.580 ms。prepare 仍占约 147–150 ms，并没有因该改动消失。这两个子 phase 已包含在整链内，不能把 prepare、project 和整链再加起来统计总收益。

缓存有内存代价：五场景端点 footprint 配对中位增加约 0.250、0.188、0.172、0.047、0.781 MiB，端点与 lifetime peak 均通过预定守护（每格允许增加至少 2 MiB 或基线的 5%）。200 是条目上限，快照中的数组与字符串大小可变，**不是字节上限**；不承诺整 App 内存减少。

正确性比较包含 items/fields/references、完整 evidence、时间范围、连线、地图点、total/partial 和诊断，不仅比较行数。手工锚点与缺失真实名称曾让合成数据被生产校验拒绝，相关失败保留；之后使用真实 `createAnchor` 和实际短原文依据，没有放宽产品验证。两臂正确性正控覆盖范围/时间隔离、新输入不复用旧结果、200 项溢出和预取消。新增 `Tests/ReadingCoreTests/CompositionSnapshotScopeTests.swift` 提供持久的公开行为回归；编译与完整 CI 状态由主执行者补充。

## 同批规模成本：用于排序下一步，不冒充已优化

辅助数据调用实际 Release Core API，8 个场景各用一个进程连续 3 次。下表 warm 为第 2–3 次的中位数，仅作规模基线，不是独立 A/B，也不是编辑器输入或搜索 UI 延迟。

| 组件与入口 | 合成规模 / 条件 | warm wall | 现有观察与下一步 |
| --- | --- | --- | --- |
| 笔记 `ReadingNoteLinkFolds.links(in:)` | 20 KiB / 5 个实际链接 | 2.274 ms | 保留 UTF-16、代码/图片排除、展开映射、IME 相关函数守护 |
| 同上 | 512 KiB / 128 链接 | 26.314 ms | 长文本解析随规模增加，值得查每次编辑的重解析范围 |
| 同上 | 2 MiB / 512 链接 | 102.729 ms | 足够大的局部成本候选；先看现有 debounce/remap 的实际触发，不直接全局缓存 |
| 搜索 `LibraryTextSearch.search` | 200 单元、未命中 | 7.110 ms | 线性扫描的小规模基线 |
| 同上 | 1,484 单元、未命中 | 51.418 ms | 扫完整书；末尾单个命中仍约 51.335 ms |
| 同上 | 6,000 单元、未命中 | 210.105 ms | 后续评估稳定有序快照/索引的优先依据 |
| 同上 | 1,484 单元、150 条结果上限 | 8.088 ms | 实际只扫描 150 单元；已有提前停止有明显作用，应保留 |

辅助运行均通过预定输出/来源检查、源字节保留和零模型/真库访问守护。笔记首次调用额外成本明显（20 KiB 首次约 14.730 ms）；不能把首次和 warm 混合宣称一个固定速度。其 RSS 随夹具规模变化，不能直接归因为泄漏。数据在 `logs/mac-batch-20261030/auxiliary/`。

知识库、关系图和组合的审计也避免重做已有工作：现有 `GraphIdentityIndex` 已构建物理节点身份索引，`BookGraphPresentationCache` 已有文档/关系快照缓存；本批没有给这些机制另加一层全局缓存，也没有把它们的既有收益记在本次账上。后续优先评估同次 UI 下游是否重复适配对象，而不是降低来源检查。

| 一手来源 / 机制 | ReadingBook 的具体对应 | 本批处理 |

| [PDF.js `watchScroll`：只为下一帧排一个滚动回调](https://github.com/mozilla/pdf.js/blob/master/web/ui_utils.js) | 当前 PDF 辅助工作已有主线程 run-loop 合并，是否仍每帧重复需实测 | 候选保留；未证明辅助工作有明显成本前不改原生滚动 |
| [PDF.js `PDFPageViewBuffer`：有界工作集并销毁淘汰页](https://github.com/mozilla/pdf.js/blob/master/web/pdf_viewer.js) | 现有 PDF 几何缓存已有限额；长期历史 WebKit 生命周期仍值得计数 | 保留现有机制，WebKit 回收作为后续证据驱动候选，未在本批实现 |

空历史提前返回是对已确定空结果的直接消除；组合 memo 是对单次不可变输入的复用。其适用性来自当前源码和本批对照，不把它们包装成某个外部项目已经替本软件证明的结果。上游 main/master 链接是研究时读取的实现，未固定为外部 commit；它们不承担本软件性能结论。没有新增依赖、复制外部实现或根据未合并 PR 宣称成熟收益。

## 共同局限及尚待补齐的交付

每个条件只有 3 对独立进程，适用于本机工程取舍，不是统计显著性、所有设备或所有书籍保证。history 进程内部的重复调用与 Chat 的 100 次输入不能扩充独立样本数。Core 结果不包括 UI、MapKit、网络或模型；Chat 结果不包括 WebContent/GPU。各数字的边界不同，不能相加成一个“全 App 提速百分比”。

收益之外已列出单 source 列表回退、快照缓存和 Chat 的 footprint 增加。完整数据/来源守护通过才构成工程候选，仍须实际产品回归。FocusState、空态建议、retry、模式重置、历史/记忆、回答保存和选区代码已作独立只读审查，未发现阻断项；该审查不替代原生 IME、Undo 与菜单交互验收。
