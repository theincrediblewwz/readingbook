# AI 怎样把原书变成阅读工作台

这轮先解决正文包装和保存回执，再用真实赤壁资料检查结果。目标仍是：问“这场仗在地图上怎么打”，就得到能看方向、能选时间、能点回原文的工作台。只保存了人物或出处，不算完成地图。

## 最值得一起推敲的五步

| 环节 | 现在怎样做 | 影响效果的取舍 |
| --- | --- | --- |
| 给哪些资料 | 按当前页、选句、章节范围及主动引用的笔记冻结本次资料范围。范围内能完整放下的原文先提供，其他内容按需读取。 | 太少会来回读取；太多会挤掉操作和回答空间。防剧透跟随用户选定范围，不按书名硬锁。 |
| 怎样给 AI 看 | 这轮把首次提供、收尾和引用纠错消息中的正文改为真正换行的原文，每段只留简短引用标题。页码、版本散列等由软件保存，AI 需要位置时单独查询。 | 原书中的代码、公式、引号和反斜线原样保留；不能把书本身的内容当杂质删掉。 |
| AI 能提出什么 | AI 可组织人物、地点、事件、时间、行动方向等共享资料，再选择或组合组件。组件声明是数据，不执行 AI 生成的程序。 | 不规定赤壁只能套一个模板；但现有类型和旧资料修订规则仍有过硬的地方，后续要调整。 |
| 软件怎样保存 | 校验出处是否实际提供、对象是否存在、旧版本是否变化。合法新增保存；需要修改已有内容时走审阅。反馈具体失败字段，让 AI 在同一任务内修正。 | 不因一处填错就丢掉前面的努力，也不能因为 AI 说成功了就当真的写入。 |
| 组件怎样显示 | 地图、时间轴、卡片和关系图引用同一批对象 ID。选时间筛选共享事件，点事件通过出处回到原文。 | 数据正确和画面好看是两层工作；不能为每个组件复制一份互相冲突的人物或时间。 |

可以把它理解为：**原书 → AI 提出整理方案 → 软件核对并保存共享资料 → 不同组件展示同一份资料**。组件是看资料的不同窗口，不是各自重新分析一本书。

## 原文里的格式为什么会出现

之前实际发送给模型的消息正文里，又放了一层 JSON：每段包含 `text`、页码、散列和引用编号。外层网络传输还会再编码一次。因此详情里的一部分 `\n` 确实是模型读到的文字包装，并非只是查看器的显示方式。

这轮保留软件内部的校验封装，只在发送正文的边界转换展示。例如：

```text
【原文 [unit:unit-000605]｜本范围完整】
这里是真正的原书第一行。
这里是真正的原书第二行。
```

标题中的 ID 用于准确引用；模型不必理解它的数字含义。需要页码或章节时，用“查询原文位置”，不必重读整段。把原句交回软件反查也有用途，但相同句子可能出现在不同页，所以保留这一点点身份信息更可靠。

“完整”只表示本次选定范围的这一片段完整，不表示整本书已经读完。模型若只拿到半页，就标为节选。短引用也只对应实际给过的文字，不能因此引用未发送的其余半页。

JSON 仍适合表达操作参数和回执。按需读取工具的返回当前也仍是结构化结果，本轮没有声称所有消息都已去掉 JSON；优先去掉的是反复携带大段原文的内层包装。认证头和 Key 不出现在请求详情里，模型的私有思考也不记录。

## 为什么要核对“实际保存”

前一轮真实模型提交了 19 条出处，复用和去重后只有 3 条是新增；没有新地图或路线。这说明“提交了几项”“保存了几项”“打开了哪个组件”必须分开。

本轮回执按真正落盘的变更区分新增、修改和移除，并按人物、事件、出处等类别计数。相同提案重放不再次算新增；数据保存回执明确只代表数据变化，组件打开仍须有自己的实际回执。最终回答应根据这些结果说明已完成与未完成。

## 验证记录

- 同一批真实赤壁原文 94 段：正文消息 143,802 → 120,402 字节，少 23,400 字节（16.27%）；正文、顺序、选段裁剪与引用身份逐项相同。单条正文消息的同条件网络封装 148,754 → 122,622 字节。不是整次请求、实际 token 或模型速度下降 16%。
- 100 次 Release 转换中位约 5.51 毫秒，P95 5.73 毫秒。不会在每次进度更新时重做原文转换。
- 最终 Core 回归为 338 方法、3,731 条独立断言，非本机 XCTest。覆盖原文换行/代码/公式、选段、同文异页、短引用、截断、位置查询权限、实际变更计数和查看器 JSON 排版。
- 最终 49 项共享工作台、43 项请求详情原生检查通过，自动门槛五类告警为零。人工离线重放的两轮功能均正常，但各有 6 条未归属 AppKit 几何诊断，严格报告标为失败并保留，不声称所有路径零告警。
- 一轮官方 DeepSeek Flash 真实试读：9 次 HTTP、报告 685,346 token、累计传输约 176.16 秒。使用同一隔离赤壁资料和相同问题；Key 仅在内存，原库禁止读写。新位置查询被实际使用，没有调用 source_read 重读原文。
- 真实结果仍未达地图目标：两个提案分别被已有事件分类冲突、时间原句与出处不匹配挡住；20 人物/地点、14 事件、25 关系、1 旧视图均未改变，没有新路线，也没有 component_show 调用。最终回答承认未保存，但仍声称提交了实际未发出的显示请求，故回答与操作回执的对应仍列部分。

### 追加反馈：详情长文本确实会卡

用户试用时指出顶部透明边、长文本展开卡住。初次现场采样已经空闲，不能冒称抓住当时持续死锁；随后用实际长正文离线复现，主线程持续在 SwiftUI 尺寸测量与 CoreText 排版中占满。

同样 65,535 字节正文，旧查看器四次展开约 15.33–15.59 秒；改用固定视口的原生只读文本查看器后约 43–61 毫秒，内容仍可选择、复制和滚动。原文片段的详情也复用该查看器。此收益只对应详情展开，不称全软件或模型提速。

顶部透明带来自自定义玻璃卡片未铺到全尺寸窗口的标题栏预留区。已让独立请求窗口的内容覆盖该区域。用户随后指出侧边仍有细框，因此又去掉独立窗口内部自绘的圆角、玻璃描边与三层外阴影，只保留原生窗口的一层轮廓。最后 CUA 画面已复核；原窗口不被挤压。

结构化结果默认提供“阅读显示 · 仅排版”，把 JSON 字符串内的正文正常换行；可以切回“原始文字”逐字核对。排版在后台准备，保留原始诊断字节，不改变实际模型请求；切换记录也不会暂时显示上一条的格式化内容。诊断单条/总量上限不变，截取处仍明确提示。

## 后续目标

先让一小组有出处的核心事件、行动方向和时间信息尽早保存并显示，再逐步补足。预算耗尽或审阅暂停后，应能接着完成剩余部分。随后按已选融合设计改善地图重叠、事件图标、曲线路线和范围示意；不先用漂亮合成图掩盖真实模型尚未完成的问题。
