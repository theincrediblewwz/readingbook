# AI任务额度与继续整理

这一轮解决的是单次任务被提前收尾、独立问题误用后台预算，以及预算结束后工具格式进入答案。它不改变原书、笔记、分析的存储，不重新组织旧书库，不改变用户保存的DeepSeek配置。

## 限制究竟是什么

安装前配置是每次任务100次模型HTTP请求，不是一本书只能问100次，也不是历史对话只有100轮。上轮真实诊断中的8次是测试宿主临时设置的付费实验上限，没有写入用户的配置。

一条问题可能连续请求模型多次，用于检索原文、检查已有对象、提交整理提案和生成答案。旧对话引擎另外提前在普通提问6次、组件提问12次收尾，即使用户设置的任务额度还有余量。现在采用实际配置的剩余请求数作为循环上限，仍为最终回答留一次机会，token和服务账户额度仍适用。默认100和界面可调范围1–2000不变，不将所有用户配置改大。

## 改动

| 问题 | 处理 |
| --- | --- |
| 读到一半一直有后台任务，新问题继承已用额度 | 并发与前台优先级全局共享；独立提问、伴读、搜索、翻译等有各自宿主拥有的任务预算。同一任务的子步骤仍共用额度，不能通过创建多个worker扩大授权。 |
| 旧任务结束清理晚到，可能影响新问题 | 结束句柄同步标记；明确绑定到worker，旧回调不能重置新预算。结束任务立即取消属于它的排队请求，即使全局槽位占满。 |
| 预算显示成全局累计编号 | 独立任务的进度从1计数，对话完成后显示自己的请求数量；全局诊断序号单独保留。 |
| 收尾重新构造提示时丢失失败原因 | 保留最近4条、每条400字以内的实际失败，明确说明不再调用工具，只报告已核验/已保存和未完成的内容；不把待审阅或失败冒充成功。 |
| 官方DeepSeek双竖线DSML进入正文 | 识别已观察到的内部封套变体，在普通答案和出处修正后的答案均拒绝；只按真实组件回执作有限确认，或明确失败保留原问题。不执行这些普通文字，不自动越过额度。代码块里的正常协议示例仍保留。 |
| 可选事件类型字段被误填为event | schema和失败回执给出本书真实类型ID及分页入口，说明可省略；kind=event不是默认类型定义。原有严格时态/原文校验不放宽，不自动把错误提案改成可写内容。 |

## 模型请求间隔

2026-11-06查阅：[DeepSeek并发说明](https://api-docs.deepseek.com/quick_start/rate_limit/)、[错误码](https://api-docs.deepseek.com/quick_start/error_codes/)、[OpenAI限流指南](https://developers.openai.com/api/docs/guides/rate-limits)。官方没有统一的固定秒数要求。DeepSeek按账户计算并发，多个Key不会各自获得一份并发额；OpenAI另有请求与token窗口，临时限流/过载应遵守Retry-After，失败重发也会占额度。

据此采用我们自己的保守策略：同一服务主机所有功能与Key共享至少1秒的请求起点间隔；通常回答本来就超过1秒，因此顺序调用不再额外等待。原来的全局并发上限与前台优先级保留，长后台任务不会锁住所有AI入口。不同服务分别计时。

服务器报告请求/token/项目token窗口耗尽时，等对应reset；429频率限制或503过载按有效Retry-After等待，并加100–300毫秒随机余量。没有提示时用2、4、8…最多60秒的递增退让。长于1小时的有效服务等待也不截短；显示给用户的错误文字仍只采用原有的短提示安全规则。额度不足/授权失败不当作临时频率问题。只有用户正常继续或新任务才触发下次请求，传输层不自动重放收费请求，更不会重放已经收到部分答案的请求。等待可取消，不阻塞主线程，也不预占未来时间槽。

只保留校验后的时长/状态数值，不记录Key、响应正文或任意响应头。这是本App进程内协调，不能控制用户在别的软件/电脑上同时使用同一账户；1秒是起点而非官方保证，不承诺绝不发生429或服务器繁忙。
