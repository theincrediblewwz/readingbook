# 阅读途中调用与组合组件

本批产品目标为 0.23.47/build78。当前实现与本机检查已完成，完整 CI、发布、安装和原书验收仍在进行；交付完成后补充最终回执。

## 现在能做什么

读者不必在开始一本书时决定全部组件。对话可以发现真实安装的组件，根据“理理人物关系”“看看这些事件的先后”等请求选择现成视图，复用本书已有入口，或追加新的入口。现成视图不足时，可以把列表、原文、关系图、时间轴、地图等已有元件组合成联动视图。不能由此生成并执行任意程序或安装新插件。

两种对话模式都能加入显示配置。新增人物、关系和文档等分析仍使用功能协作和当次整理权限；修改已有内容继续审阅。组件配置与整理结果分开报告，空组件不能当作分析完成。

“读到这里”是一个显式范围：开头至当前整页。它不是已读页统计，也不自动扩大当前页的授权。所有检索、原句、笔记与保存证据仍经过原有范围校验。

## 追加、复用与冲突

目录来自实际渲染注册表，返回用途与分页的已有视图，不按中文关键词在宿主中硬编码用户意图。未知组件、停用声明包和未保存笔记分别返回可读状态。打开成功以实际导航完成为准，不以发出请求为成功。

已有的正文内嵌组件不会冒充侧栏入口：保留内嵌声明，另加导航视图，随后复用；停用声明包仍不能被复制绕过。

新入口在仓库 actor 内读取最新项目后追加，保留同时保存的笔记、分析和其他组件；组合视图保存现有的受限声明。同一轮先加入入口、再整理内容时，只跟进本轮自己的追加，不宽免用户或其他任务的中途编辑。换书、切库、原书版本变化、取消和旧请求均不能把迟到操作带入新界面。

## 本机证据与性能限度

- `logs/dynamic-components-20261104/adopted47-core/` 与 `adopted47-format/`：16 + 13 个当前测试体，以本机独立断言运行，67 + 47 项通过。这不是 XCTest；完整 XCTest 交由 CI 执行。
- `adopted47-native1/2/`：真实 AppStore、对话引擎、仓库、组件注册表及完整工作区，两轮各 26 项检查通过，四类运行时警告均为零，网络被沙盒禁止。覆盖先开图再保存有证据关系、重复复用、组合创建、重载、草稿保护、未知组件与跨库/旧请求保护。模型输出是确定性夹具，不能以此代替实模型的意图判断。
- `show-baseline-2/3` 与 `show-candidate-1/2`：相同预热条件下，8 次重复调出已有视图的当前书发布从 8 次降到 0 次。CPU 两进程中位数约 114.25→108.31ms，差异较小、样本少，不宣布显著 CPU 加速，更不外推 FPS、整体启动或内存。采用依据是消除可精确验证的无效加载和发布。
- `show-baseline-1` 未使用同样的预热条件，排除于正式比较。基线产品对象与 `native-third/build-manifest.json` 相同；后两次基线取证时本地另有一处尚未编入对象的仓库组合范围校验，其源码漂移另行记录，不把该处文本冒充基线编译输入。优化目标文件与基线对象对应，候选有独立冻结的完整源码/对象清单。

“读到这里”的保存格式使用旧版认识的 `book` 范围字段，加可选的精确范围策略；新版本恢复原语义，旧版仍可解码。原文单元与指纹不变。`legacy-scope-before.json` 为旧解码失败证据，`legacy-scope-after.json` 与当前 Core 回归为通过证据。

实模型验证使用已配置服务与合成短文，没有读取或写入原书库。早期试验发现输出截断，以及服务将内部 DSML 工具格式当作正文返回的情况；失败原始记录保留。仅增加一次格式重试仍不稳定，进一步按 [DeepSeek V4.1 官方编码说明](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/main/encoding/README.md)处理新旧标记差异。

兼容范围严格限制为 DeepSeek V4 系列模型、完整 assistant 组件调用信封、当轮实际提供的两个组件工具。字符串按原样保留，其他参数按 JSON 解码，随后仍通过原有类型、范围、预算和宿主所有权校验；未知工具、写入提案、混杂说明、重复字段、截断或超限信封不恢复。没有将普通书中标记、任意代码或未经授权的提案当作操作执行。无法识别的内部格式仍最多重试一次，不写入回答。最终实模型结果另列，不把夹具通过写成模型判断必然正确。

最终 `live-adopted47/` 中两种自然问法均完成真实组件选择与自然语言回答，未使用回执兜底。该实验只验证模型选择：宿主为不写入的回执接口；实际保存、导航、重载及组合由上述生产工作区夹具验证，不把两种证据混为一谈。此前失败原始记录继续保留。

实测还发现旧的固定六轮问答上限，会在模型查完人物后、尚未打开组件前强制结束。提供组件能力时改为最多十二轮，仍受用户当次请求和 token 上限约束；回归确认用户只给六轮时绝不突破。混在说明末尾的完整内部调用标记也不能作为回答保存。已经真实完成的界面操作和模型文字说明分开处理；说明格式失败时只据真实成功回执确认操作，不伪称完成分析。

## 负尺寸警告的定位

本批抓到的六个负尺寸调用全部是 `-1`，调用链为 `_NSViewValidateGeometry → NSViewValidateSize → NSView.setFrameSize → NSThemeFrame._positionSharingIndicator`，其上游包含 `NSWindowSharingSessionRecipientIndicator`。这是系统的窗口共享提示器。

独立最小 AppKit 窗口只有一个文字标签，没有 SwiftUI、PDFKit、WebKit 或 ReadingBook 组件：读取界面前 0 条，读取后同样产生 6 条。见 `minimal-window/comparison.json`、前后系统日志、可见窗口截图和 `geometry-negative-stacks-final.log`。这推翻了“隐藏阅读面板尺寸为零”的本批假设。没有因此改阅读布局、屏蔽系统日志或放宽原生回归门槛；也不把没有逐条采栈的历史警告全部自动归为同一原因。
