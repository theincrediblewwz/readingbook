# 从 Minecraft 性能模组借鉴什么

用户提出的“固定世界、移动摄像头、只准备附近内容”适合 ReadingBook。下面按 2026-11-05 查到的项目原始说明和代码整理；右侧是结合本仓库源码作出的应用判断，不是这些模组已经为 ReadingBook 带来的收益。没有下载游戏或模组，也没有引入新的依赖。

## 思路与本软件的对应关系

| 项目与原始资料 | 值得借鉴的机制 | ReadingBook 的对应工作 |

| [Minecraft 官方：显示距离与模拟距离](https://learn.microsoft.com/en-us/minecraft/creator/documents/simulationrenderdistanceguide) | 显示范围、持续运算范围和特别保留的活动区域各自管理。 | 原书、笔记、分析长期保存；可见视图按需创建；正在编辑、拖动、保存的对象即使暂时离屏，也不能突然销毁。 |

| [Distant Horizons](https://gitlab.com/distant-horizons-team/distant-horizons) | 远处以简化表示替代完整区块，保留整体轮廓。 | 图谱远景可研究“概览细节级别”：保留人物/主题分布、主要连接和选中对象，靠近后显示完整卡片。地图可以研究聚合标记。它会改变远景外观，应先出交互稿，不能静默隐藏用户正在查找的内容。 |

| [FerriteCore 的机制说明](https://github.com/malte0811/FerriteCore/blob/main/summary.md) | 减少重复结构、过度对象层级及不必要的闭包持有。说明中有明确的历史版本和测试环境。 | 先用分配栈确认重复实例，再共享不可变的派生资料。不能把旧游戏环境的节省 MB 数字套到本机，也不能将用户原文、便签或分析进行有损合并。 |

| [EntityCulling](https://github.com/tr7zw/EntityCulling) | 后台判断真正可见的对象，特别处理超出普通包围框的对象和白名单。 | 借鉴可见集合与特别保留对象：正在编辑的节点、跨视口连线、选中地点及其说明不能只按中心点裁掉。二维界面先用可靠的边界判定，不引入游戏三维射线追踪。 |
| [Exordium](https://github.com/tr7zw/Exordium) | 将HUD与世界绘制分开，降低HUD固定刷新频率来让出CPU/GPU时间。 | 对应思路是确认静态工具栏、被遮挡的组件是否仍重复准备，而不是给整个阅读器降帧。悬停、拖动、便签展开和翻页仍须及时刷新；SwiftUI已经避免的静态更新不再“优化”一遍。该项目也明确提示部分屏幕效果存在透明度问题，不能直接照搬到玻璃控件。 |

Sodium 是性能模组，不是 Minecraft 原版引擎的全部实现。各项目负责的层次不同，可以学习共同原则，不能把它们的游戏性能百分比相加，或当作 ReadingBook 的预计收益。

本表只是机制研究，没有复制第三方实现。尤其不能把“降低不必要绘制”理解为全局降低交互刷新率：用户要求的流畅翻页、悬停反馈和便签动效仍是验收条件。

## 与这轮实验的关系

本仓库的 `GraphCamera` 已经保持节点世界坐标不变；相机平移和缩放只改变显示变换。连线几何和节点身份也已有缓存。现在需要减少的是相机变化时仍然重复发生的界面构建。

本轮关系标签复用候选已完成两个规模各三次新进程对照。1,024 节点下，固定 24 次更新的近景平移、远景平移和混合缩放 CPU 中位数分别下降约 18.5%、26.0%、8.0%；静态六组画面逐像素相同。它没有删减远景内容或改动节点坐标。31 项真实标签输入、改名、失败重试、当前回调、换库和回收检查通过。正式采用和交付状态另见本轮结果，不将此文当作安装回执。

“分块查询”也已做查询级原型：1,920 组有序结果与原有全扫描一致。在 1,024 节点下，原查询每次仅几微秒，当前收益不足以抵偿新增索引与失效规则；六万多个节点的局部视口查询则显示出价值。此原型没有并入产品。远缩放时大部分节点本来都在视口内，空间索引也不能替代细节分级和降低绘制成本。

全局地图已经测到大量原生标记随相机更新重复准备；单纯给标记套复用层的首个大规模配对只改善约 5%，低于本次采用门槛，尚未合入。另一个相机绑定边界候选也已验证：实际地图仍能更新，但没有减少标记重建，未采用。下一步研究把静态MapContent与相机持有者分开，以及原生标记复用/聚合或批量绘制，不直接更换地图引擎。

## 优先借鉴哪些

结合本轮采样，优先次序不是按模组名气决定：

1. **先减少界面构建与绘制提交。** 当前1,024对象的地图主要时间花在标记视图，图谱远景主要是大量文字/交互视图；查询只占几微秒。优先借鉴批量提交和原生标记复用，测整个操作耗时。
2. **再决定远景表示。** 大多数节点已经进入画面时，继续缩小查询范围意义有限。概览应保留选中项、整体分布与主要关系，放大恢复完整；实际显示与给AI的可见信息必须对应。交互稿确认后再改外观。
3. **后台准备按预算衔接。** 预取边界、线程数、待提交结果都有限制；快速移动只保留当前所需。原书和分析作为持久数据保存，缓存有上限；编辑、保存和用户启动的AI任务有独立生命周期。

Exordium的降低固定刷新率做法不作为本轮候选：目前没有证据证明静态HUD在重复高频绘制，直接降帧也会损害用户要求的动效。EntityCulling的三维射线同样不适合直接迁入二维图谱；本软件需要的是准确的二维可见集合和长连线边界。

## 后续顺序和保护

1. 先完成当前已证实候选的完整回归、GitHub 和安装交付，原书、笔记、分析保留。
2. 地图和图谱继续按“数据、可见集合、绘制表示、输入命中”分层。离屏只减少显示工作，用户已经启动的伴读/对话任务继续遵守现有独立调度，不能照搬游戏模拟距离而停掉。聚合后的可见对象声明也必须符合真实画面，不能把隐藏正文当作用户已看过。需要改远景外观时，先给出保持完整模式和自动概览模式的设计对比。
3. 后台准备采用有界任务队列和视口优先级；预取只保留有限边界，不能无限缓存。取消和换书必须检查当前身份。
4. 再独立核对启动、硬件滚动 FPS、主程序/WebKit 进程组与空闲负担。当前 CPU 对照、诊断模式分配数据不冒充这些指标。

所有实验、构建和原始记录仍留在工作目录；按批清理结束的程序副本与重复产物，保留必要回滚和关键成功/失败证据。
